# Six Tool Cross-Tool Patterns

稽核日期：2026-09-10｜Repo：`sytax-academy/shengyan-tools` @ `dd81fdc`｜Mode：`REVIEW-ONLY`

依 control pack 要求，跨工具型態**在各工具層級發現記錄完成之後**才作成。本檔所列型態，皆以六支工具逐一量測的結果為基礎，不以任一工具的結論反推另一工具的 Product Rule。

---

## 0. 一句話總結

六支工具個別品質不低，但**彼此之間沒有共用的技術契約**：同一件事（驗證、持久化、事件註冊、匯出、landmark、版本標示）在六支工具中有多達六種做法，而且每一種的品質差距很大——最好的實作與最差的實作同時存在於同一個 repo 內。

## 2. CT-06｜三套互相矛盾的數值輸入定義域

**這是六個型態中影響最直接的一個**，因為三支工具面對的是同一批學員、掛在同一個品牌下、處理的都是新台幣金額。

對三支工具施以**同一組輸入類別**，結果如下：

| 輸入類別 | 4-1 損益兩平 | 4-3 現金流量 | 2-2 投保級距 |
|---|---|---|---|
| 負值 `-100` | 拒絕：`本工具不支援負值，請填 0 或正數` | 拒絕，暫停 autosave | **靜默無反應** |
| 非數字 `abc` | 拒絕：`請輸入一般數字，最多 2 位小數…` | 拒絕，暫停 autosave | **靜默無反應** |
| 科學記號 `1e9` | 拒絕 | 拒絕，暫停 autosave | **靜默無反應** |
| 超長位數 | 拒絕（精度超限訊息）| 拒絕，暫停 autosave | **接受**（999,999,999 → 人事成本 1,000,028,317）|
| 多位小數 | **拒絕**（上限 2 位）| **接受**（3.14159 判為有效）| **接受**（28,590.7、0.4）|
| 空字串 | 正確視為非錯誤 | 正確處理 | 靜默無反應 |
| `aria-invalid` | **有設置** | 有 invalid 樣式 | **從不設置** |
| 錯誤訊息 | **每類對應具體訊息** | 每類對應具體訊息 | **無** |

三支工具對「多位小數」給出三種不同答案（拒絕／接受／接受），對「是否告知使用者」給出兩種不同答案。一位在 4-1 被告知「最多 2 位小數」的學員，在 4-3 可以填 5 位，在 2-2 可以填任意值且不會被告知任何事。

**技術面可確認**：三者不一致。
**不可確認、需 SOT**：哪一套才是正確的定義域。小數精度、金額上限、是否允許零，都取決於各工具的 Product Contract，不在 repository 內。

**建議**：先由 SOT 決定全家族統一的數值輸入契約（正負、量級上限、小數位數、拒絕的呈現方式），再一次套用三支。4-1 的實作是最完整的起點——它已經有 per-field 錯誤節點、`aria-invalid`、`aria-describedby` 與分類訊息，可直接移植。

## 3. CT-05｜完全無測試基礎建設

Repository 共 14 個 tracked 檔案：6 個 `index.html`、6 個 `README.md`、`DEPLOYMENT.md`、`README.md`。**沒有** `package.json`、測試目錄、`.github/workflows`、linter 或 formatter 設定。

`DEPLOYMENT.md` 以文字定義了相當嚴謹的 release gate：

> 5. 只有通過 Release Identity Lock 的正式 Runtime 才可部署。
> 6. `LIVE` 只用於 Release LOCKED + Deployment DEPLOYED + Verification PASS。
> 7. `NOT EXECUTED` 不得視為 PASS。

這些規則本身寫得好，但**背後沒有任何可執行的檢查**。「Verification PASS」目前沒有對應的可重跑程序，因此第 7 條的「不得視為 PASS」在實務上無從自動落實。

**代價已經發生過一次**：3-2 v1.5.6 的搜尋 regression（T32B-01）進入正式環境，直到實際使用才被發現並回退。該 regression 的形態是「三個常見查詢回傳釐清提示而非結果」——這正是一組 query-to-outcome 表格式測試能以近乎零成本攔截的類型。

**這些工具異常適合自動化測試**：自足靜態 HTML、無 build、無 server 依賴、無資料庫、無 fixture、無認證。本次稽核所用的全部 harness 都是為此次執行臨時搭建、隨即拋棄的；把它固化下來的邊際成本很低。

**另一個代價是本報告本身**：目前 4-3 的惡意匯入防護（含 prototype pollution 阻擋）、autosave 錯誤閘門、3-2 的搜尋行為、4-1 的驗證訊息表——這些正確行為的正確性，唯一的書面記錄就是本次稽核。repo 內沒有任何東西保護它們不被下一次改版無聲破壞。

## 4. CT-04｜同一能力兩套實作

4-1 與 4-3 都提供 XLSX 匯出，實作方式完全不同：

| | 4-1 | 4-3 |
|---|---|---|
| 方式 | 自製 writer，約 200 行 | 內嵌 SheetJS 0.18.5 |
| 位元組 | 併入應用程式碼 | **639,125**（佔全檔 84%）|
| 組成 | `xlsxEsc`、`xlsxColName`、`xlsxSheetXml`、`xlsxMakeCrcTable`、`xlsxCrc32`、`xlsxU16`、`xlsxU32`、`xlsxCat`、`xlsxZipStore` | `XLSX.utils.book_new`、`book_append_sheet`、`aoa_to_sheet`、`XLSX.writeFile` |
| 產出 | 13,018 bytes、7 entries、3 sheets | 22,519 bytes、10 entries、含 styles/theme |
| 驗證結果 | 合法 ZIP + OOXML | 合法 ZIP + OOXML |

兩者都能產出合法檔案。問題是一個能力有兩個維護面與兩類 bug。

**同時這是解決 T43-04 的現成路徑**：4-1 已經證明不需要 vendor bundle 也能產出合法 workbook，體積是 1/50。若統一採用 4-1 的 writer，SheetJS 0.18.5 連同其在依賴掃描中的版本告警可一併消失。

**遷移前必須確認的技術點**：4-3 匯出的是**含公式**的工作表（`SUM(...)`、跨欄參照、期初餘額承上月的公式鏈），而 4-1 的 writer 目前處理的是 inline string 與數值儲存格。統一前需先確認 4-1 的 writer 支援 formula cell（`<f>` 元素），否則 4-3 的匯出會從「可再計算的試算表」退化為「靜態數字快照」——那是功能損失，不是重構。

## 5. CT-03｜事件、狀態、驗證三種策略各行其是

### 5.1 事件註冊

| Tool | inline `on*` | `addEventListener` | 形態 |
|---|---|---|---|
| 2-1 | 10 | **0** | 完全 inline，呼叫全域 `answer()`/`back()`/`restart()` |
| 1-1 | 4 | 1 | **混用** |
| 3-2 | 0 | 8 | 委派式監聽（`data-*` 屬性驅動）|
| 4-3 | 0 | 16 | 監聽器 |
| 4-1 | 0 | 18 | 監聽器 |
| 2-2 | 0 | 26 | 監聽器 |

三種慣例（全 inline／混用／全監聽器）並存。2-1 的做法使該工具無法在禁止 inline handler 的 CSP 下運行，並在全域命名空間留下三個函式名。1-1 的混用則使維護者必須查兩個地方才能找到某個控制項的處理邏輯。

### 5.2 監聽器從不移除

`removeEventListener` 在六支工具中**全部為 0**，而 `innerHTML` 重寫式渲染每支有 6 到 18 處。

**本次未能證明存在監聽器洩漏**：重複渲染的目標節點與掛載監聽器的節點看來並非同一批。因此這裡記錄的是**待驗證的風險**，不是已確認的缺陷。建議的驗證方式已列入 `Six_Tool_Test_Inventory.md`（完整重渲染週期前後的監聽器計數探針）。

### 5.3 持久化

| Tool | 持久化 |
|---|---|
| 4-3 | **完整**：localStorage 自動保存 + JSON 匯出/匯入 + 復原模式（normal / recovery / bridge）+ 錯誤閘門 |
| 其餘五支 | **無**，狀態僅存於記憶體 |

4-3 的持久化設計相當周到（無效輸入時暫停保存並保留上一版、匯入失敗時明示原有進度未被覆寫），而其他五支完全沒有。這在 4-1 上造成具體後果：使用者填完完整成本模型後，一次誤點 `#resetBtn` 即全部消失且無從復原（T41-02）。

### 5.4 綜合建議

把六支工具中**已經是最佳解**的實作抽出為共用 baseline：

- **驗證層** → 取 4-1
- **持久化與匯入防護** → 取 4-3
- **委派式事件與輸入跳脫** → 取 3-2
- **標題與 landmark 結構** → 取 3-2（唯一 `main`/`header`/`footer` 齊備且標題完整者）
- **CSS 紀律** → 取 2-2（唯一零重複宣告者）

值得強調：**這五項最佳實作分散在四支不同的工具裡**。沒有任何一支工具同時具備全部五項。這正是 CT-03 的本質——不是品質不足，而是好的做法沒有擴散。

## 6. CT-02｜landmark 使用不一致

| Tool | `main` | `header` | `footer` | `nav` |
|---|---|---|---|---|
| 1-1 | 有 | 無 | 無 | 無 |
| 2-1 | 有 | 無 | 無 | 無 |
| 2-2 | **無** | 有 | 有 | 無 |
| 3-2 | 有 | 有 | 有 | 無 |
| 4-1 | **無** | 有 | 無 | 有 |
| 4-3 | **無** | 有 | 無 | 無 |

六支工具有六種不同的 landmark 組合。使用輔助技術的學員從索引頁逐一開啟這些工具時，每一支的文件骨架都不一樣，無法建立一致的瀏覽習慣。三支缺 `main` 者，skip-to-content 無落點。

3-2 是唯一 `main`/`header`/`footer` 齊備者，可直接作為統一骨架的範本。

## 7. CT-01｜頁面 metadata 全體缺失

六支工具**全部**沒有 meta description、favicon、theme-color。

| Tool | description | favicon | theme-color |
|---|---|---|---|
| 全六支 | 無 | 無 | 無 |

這些是公開掛在 GitHub Pages、且 `DEPLOYMENT.md` 記載即將切換至品牌網域 `tools.sytaxes.com` 的工具。無 description 時，搜尋引擎與社群分享會自行截取頁面開頭文字作為摘要；無 favicon 時，瀏覽器顯示預設圖示，並會發出 `/favicon.ico` 探測（本次稽核初期觀察到的 console 404 即源於此，見報告 NR-03）。

一致地缺失，也就一致地容易補：六支共用一份 header 片段即可。

## 8. 未構成跨工具型態的事項

以下事項在多支工具中出現，但經檢視**不構成需要處理的型態**，記錄以免日後被誤判為系統性問題：

| 事項 | 為何不構成問題 |
|---|---|
| 六支皆無 `prefers-color-scheme`（深色模式）| 一致的產品決定，非缺陷。工具為淺色設計且對比充足 |
| 六支皆無 `<form>` 元素 | 皆為即時計算工具，無提交行為，不需要 form |
| `innerHTML` 使用普遍（6–18 處/工具）| 已逐一檢視插值來源：3-2 的使用者輸入經 `esc()` 跳脫；4-1 的 `data.message` 為程式內字面值；4-3 皆為內部資料。**無使用者可控的注入路徑** |
| 版本字串與發布版不符（1-1、4-1）| 已個別列為 T11-01 / T41-04。兩支雜湊皆與 manifest 相符，屬標示漂移而非錯誤 artifact |
| 檔名為 `index.html` 而非 manifest 所列帶版號檔名 | 為 `DEPLOYMENT.md` 明定的部署規則，且雜湊逐一相符，非身分疑義 |

## 9. 跨工具建議的處理順序

1. **CT-05（測試基礎建設）** 應最先動工，因為其餘各項的驗收都需要它。且它是唯一能防止 T32B-01 類事件重演的措施。
2. **CT-06（數值輸入契約）** 需先取得 SOT，因此宜與第 1 項平行啟動——取得 SOT 通常比寫測試慢。
3. **CT-02 / CT-01（landmark 與 metadata）** 為機械性、低風險，可在一次「共通 header 與 a11y 收尾」中合併處理。
4. **CT-04（統一 XLSX 匯出）** 應在 CT-05 之後進行，因為它需要匯出結構斷言作為安全網；並須先確認 formula cell 支援。
5. **CT-03（共用 baseline）** 是長期方向而非單次修復，建議在下一支新工具開發時以抽出的 baseline 起步，既有六支則隨各自改版逐步收斂。
